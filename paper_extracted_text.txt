Abstract
With growing demands from memory-bound applications, Processing-
In-Memory (PIM) architectures have emerged as a promising way
to reduce data movement. However, existing PIM designs face chal-
lenges in compatibility and efficiency due to limited command/address
space and the overhead of switching between PIM and normal mem-
ory modes. To address these limitations, we propose ComPASS, a
compatible PIM protocol and scheduling solution that enables effi-
cient processor-PIM integration. ComPASS introduces PIM-ACT,
a new memory command that triggers multi-bank activation and
PIM operations at once, allowing for compatibility across diverse
PIM architectures. It also adds a PIM request generator within the
memory controller, which can serve all PIM devices compliant with
PIM-ACT, avoiding device-specific integration. In addition, Com-
PASS supports architecture-aware optimizations, enabling each
PIM device to use a customized PIM-ACT configuration tailored to
its architecture without compromising compatibility. For efficient
scheduling of both PIM and conventional memory requests, Com-
PASS proposes static and adaptive scheduling that maintain PIM
throughput while allocating bandwidth to conventional workloads
for overall system efficiency. Our evaluation shows that ComPASS
consistently meets PIM performance targets by achieving up to
10.75× GEMV speedup on LPDDR-PIM over non-PIM environments,
even under co-execution with memory-intensive CPU workloads,
thereby demonstrating both efficiency and compatibility.

1 Introduction
Processing-In-Memory (PIM [ 1, 2, 5, 8, 12, 16, 18, 25, 29, 48, 52,
55, 58, 61, 64]) presents a promising solution to address the mem-
ory bandwidth limitation in memory-intensive operations, such
as general matrix-vector multiplication (GEMV), which is widely
used in large language models (LLMs [4, 6, 11, 57, 62]) inference.
Unlike conventional architectures that require data transfers from
memory to processor, PIM architectures implement computational
capabilities directly within memory arrays. They mitigate data
movement overhead between memory and processors, yielding
significant performance improvements. For example, to perform
GEMV operation, traditional architectures must repeatedly fetch
non-reusable matrix data from memory, whereas PIM architectures
leverage memory internal bandwidth by computing in multiple
processing units (PUs) within each bank using the locally stored
matrix data in parallel. This approach dramatically reduces off-chip
data transfers, leading to both faster computation and lower power
consumption [16, 40, 59]. As a result, PIM systems offer substantial
efficiency and performance gains in environments constrained by
power or bandwidth, from edge devices to data centers.
PIM devices can be equipped with CPUs or GPUs as replacements
for conventional memory [10, 38, 40], and recent real-world PIM de-
vices illustrate varying trade-offs in programmability, compatibility,
and system integration. UPMEM-PIM [10] integrates RISC-based
processing units (PUs) into DRAM devices, enabling in-memory ex-
ecution of entire applications. It uses a protocol compatible with the
JEDEC DDR4 standard [19], allowing it to be deployed as a drop-in
replacement for conventional DDR4 DIMMs. Although it occu-
pies standard main memory slots, UPMEM-PIM cannot function as
main memory as memory access from general user applications is
restricted and entirely blocked during PIM execution.
In contrast, HBM-PIM [35, 40] and GDDR6-AiM [38] accelerate
specific operations like GEMV rather than running entire applica-
tions. Thus, they must be tightly integrated with the processor and
work in conjunction with it to complete end-to-end applications.
HBM-PIM adheres to the standard HBM2 interface [21] and sepa-
rates memory modes into normal and PIM modes to employ con-
ventional memory commands (i.e., reads and writes) to trigger PIM

workloads cannot be processed while in PIM mode, and switching
between memory modes incurs non-negligible latency because it
requires a predefined sequence of commands to change the mode.
Consequently, conventional applications can suffer from significant
memory access latency. GDDR6-AiM [ 38] extends the standard
GDDR6 interface with new compute and data commands, enabling
it to handle both standard memory and PIM requests without mode
changes. However, this approach requires a dedicated memory sub-
system for new commands or modifications to the processor-side
memory controller (MC), which are specific to GDDR6-AiM and
cannot be reused for other PIM architectures. As a result, adopt-
ing GDDR6-AiM necessitates PIM-specific customization of the
memory interface, limiting its portability and general applicability.
While real-world PIM architectures have proven effective for
accelerating memory-bound applications, their integration into
general-purpose systems remains limited due to protocol constraints.
First, these protocols do not support fine-grained interleaving of
memory requests from the processor and PIM, requiring explicit
mode switching or coarse-grained serialization. This becomes par-
ticularly problematic in systems where PIM must serve not only
as a compute engine but also as general-purpose memory, such as
mobile or edge platforms, and also leads to scheduling challenges
in coordinating memory access between the processor and PIM.
Prioritizing PIM execution excessively delays normal memory re-
quests, whereas prioritizing host memory access can lower PIM
throughput and violate Quality-of-Service (QoS) for PIM workloads.
Second, compatibility remains a significant challenge. For exam-
ple, GDDR6-AiM supports fine-grained interleaving but requires
modifications to the memory subsystem, including the MC, to sup-
port new commands. Such incompatibility hinders adoption, as
each PIM design requires custom host integration, increasing hard-
ware complexity and preventing wide deployment across platforms.
Therefore, a compatible PIM protocol must be designed to comply
with existing DRAM standards, particularly considering the limited
command/address (CA) space of commodity memory interfaces.
To address these challenges, we propose ComPASS, a compatible
PIM protocol architecture and scheduling solution that enables effi-
cient collaboration between the processor and PIM devices. Consid-
ering the limited CA space and the fact that most PIM architectures
initiate execution via multi-bank activation (ACT), we introduce
a new PIM command, PIM-ACT, which activates multiple banks
and initiates a specific PIM operation simultaneously. It includes an
optype field that allows each PIM device to define its own semantics,
supporting architectural diversity while maintaining compatibil-
ity. To reduce command transmission overhead, we incorporate a
PIM request generator in the MC, which autonomously generates
PIM requests, alleviating the burden on processor cores. We fur-
ther show that ComPASS can efficiently support PIM operations,
which do not use multi-bank ACT, through architecture-aware PIM-
ACT optimization, and can be applied to existing PIM devices such
as HBM-PIM [40] and GDDR6-AiM [ 38]. Moreover, we propose
two scheduling solutions, static and adaptive throughput balancers,
that coordinate PIM and normal memory requests. These ensure
that general-purpose workloads are served without excessive delay,
while maintaining consistent performance for PIM execution. We
evaluate ComPASS using microbenchmarks and GEMV operations
from GPT-3 inference (6.7B and XL models [6]), representing typi-
cal PIM workloads. Our results show that ComPASS meets token
generation latency targets where the processor runs various com-
binations of SPEC CPU 2017 workloads [ 56] and multi-threaded
GAP Benchmark Suite (GAPBS [3]) workloads concurrently with
PIM. The key contributions of this paper are as follows:
• We propose a new PIM command, PIM-ACT, and the memory
subsystem with PIM request generator to establish a compatible
PIM protocol that can be adapted to various PIM architectures.
• We introduce two scheduling solutions, the static and adaptive
throughput balancers, to manage PIM and standard memory
requests, ensuring memory access for general workloads while
maintaining consistent PIM performance.
• Through simulations accelerating GEMV operations for GPT-
3 inference workloads, we demonstrate that ComPASS meets
token generation latency requirements, achieving 10.75× GEMV
performance improvement over the system without PIM even
when memory-intensive SPEC CPU workloads run together.
2 Background: Real-world PIM Devices
Recently, Processing-In-Memory (PIM) devices from DRAM manu-
facturers [10, 35, 38, 40] have proven viable in real-world systems.
They leverage DRAM bank-level parallelism, employing a SIMD
structure to access and process data from each bank in parallel with
a single instruction.
UPMEM has commercially released UPMEM-PIM [10], the first
programmable PIM device, implemented in the form of DDR4-2400
DIMMs [19]. Each DRAM chip of UPMEM-PIM contains a Data
Processing Unit (DPU) per bank to enable parallel computations
across DRAM banks and accelerate memory bandwidth-limited
applications (Figure 1(a)). Each DPU is a RISC-based processor
that operates with ISA composed of dozens of instructions. PIM in-
structions are stored in the DPU’s IRAM and executed sequentially.
Additionally, each DPU is equipped with WRAM, which serves as a
scratchpad or cache, enabling efficient access to reusable data. Since
UPMEM-PIM can perform various computations flexibly through
DPUs, it can be considered a general-purpose PIM, and the ad-
dress space of UPMEM-PIM is isolated from the main memory, so
it functions similarly to an accelerator from the CPU’s perspective.
Some PIM devices [35, 38, 40] focus on accelerating specific op-
erations that dominate key workloads (i.e. domain-specific PIMs).
Samsung’s HBM-PIM [35, 40], designed for GEMV and element-
wise operations, extends HBM2 by integrating one PU per two
banks (Figure 1(b)). Each PU consists of sixteen FP16 FPUs and sev-
eral register files GRF_A/B for vector data, SRF for scalars, CRF for
PIM instructions, and control registers. HBM-PIM supports three
modes–SB, HAB, and HAB-PIM–to distinguish PIM operations
from standard memory access using JEDEC-compliant commands.
In SB mode, each bank independently handles standard memory
requests. In HAB and HAB-PIM modes, all PUs in a channel and
their associated banks (even or odd banks) operate in parallel. HAB
mode allows updating PU registers through DRAM write (WR) com-
mands, while HAB-PIM mode enables concurrent bank access and
PU execution using read (RD) or WR commands. Mode switching
is triggered by a predefined sequence of memory commands sent
to specific addresses. To initiate PIM execution, the host switches

a different row, all banks must be precharged, and new rows are
activated in parallel through another multi-bank ACT.
3 Motivation
The rise of LLMs has driven interest in domain-specific PIM archi-
tectures to accelerate key operations, prompting efforts to integrate
PIM into systems from data centers to mobile platforms [17, 39, 46,
54]. However, broad PIM adoption still faces two major challenges:
protocol compatibility and memory scheduling. First, a general-
purpose protocol is needed to integrate PIM without major modifi-
cations to existing DRAM standards. Without such a protocol, each
PIM design requires separate changes to the memory subsystem,
increasing integration costs. For example, GDDR6-AiM [38] intro-
duces over a dozen custom commands, requiring a dedicated mem-
ory subsystem only for itself. HBM-PIM [40] adheres to HBM2 [21]
standards but incurs latency overhead from mode transitions. A
complete round-trip transition between PIM mode and normal
mode takes approximately 350ns, during which memory access
is entirely stalled. This overhead makes frequent mode switching
highly inefficient. The LPDDR-PIM [28], still under development,
proposes additional commands to ease mode transitions, but this
approach is ineffective for architectures that do not rely on such
mechanisms. Thus, a compatible protocol is essential to reduce
system complexity and ensure interoperability across PIM designs.
Second, domain-specific PIMs require frequent coordination with
the host processor, as they cannot independently execute full work-
loads. Also, since they often serve as main or device memory, PIM
operations must coexist with normal memory traffic. However, PIM

system responsiveness. Also, frequent switching between PIM and
normal requests incurs bank-state transition overhead, while long
uninterrupted bursts of either type can starve the other, violating
QoS. Thus, a balanced scheduling policy is required to optimize
memory bandwidth utilization while minimizing such disruptions.
Designing such a solution must also consider hardware con-
straints. The limited CA width defined by JEDEC standards re-
stricts the number of additional PIM commands. While reserved-
for-future-use (RFU) commands can be leveraged, they are scarce
(e.g., DDR5 provides only four [22]). LPDDR5 and GDDR6 offer even
less availability, lacking RFU commands [ 23, 24]. In these cases,
repurposing don’t-care bits in existing commands, such as NOP (No
operation), may offer a partial solution—but the number of usable
commands remains limited. Thus, the protocol must be designed to
accommodate these constraints while maintaining broad compati-
bility across devices, enabling unified host-side implementation.
To address these challenges, we propose ComPASS, a compatible
PIM protocol and scheduling solution for efficient PIM integration
in modern systems.
4 Compatible PIM Protocol and System Support
4.1 PIM-ACT: A Memory Command for PIM

operational patterns across PIM devices. Many PIM architectures
exploit bank-level parallelism by activating rows in multiple banks
and accessing data concurrently during computation. For example,
in GEMV, each bank activates a row containing part of the matrix,
and each PU performs multiply-and-accumulate (MAC) operations
using vector data in its register (e.g., GRF_A in HBM-PIM [40] or
the global buffer in AiM [10]). For writing register values to DRAM,

Based on this observation, ComPASS introduces a new mem-
ory command, PIM-ACT, which simultaneously activates rows in
multiple banks and allows subsequent column commands (e.g.,
RD) to encode and trigger specific PIM operations. The MC issues
PIM-ACT with a row address and a PIM operation type (optype),
which defines the operation semantics. Following PIM-ACT, col-
umn commands are broadcast to multiple banks and interpreted
according to the specified optype. Each PIM architecture can define
its own optype set according to its operations, while still adhering
to the common protocol semantics. This design allows different PIM
devices to communicate with the host using the same PIM-ACT
interface, ensuring compatibility.
PIM-ACT is implemented using RFU commands defined in vari-
ous JEDEC standards (Figure 3). In DDR5 [22], one RFU command
is used to support up to 64 distinct PIM operations. In LPDDR5 [23]
and GDDR6 [24], which lack RFUs, we repurpose don’t-care bits in
the NOP command to encode PIM-ACT. To overcome the limited
CA width, we adopt a multi-cycle command format, allowing both
the row address and optype to be delivered over multiple cycles.
LPDDR5 already divides ACT into ACT1 and ACT2 across two
cycles, so we leverage and extend it as illustrated in Figure 3(b) and
(c). This format requires additional decoding time, increasing tRCD
(row-to-column delay) for PIM-ACT by one cycle.
PIM devices can be designed to recognize PIM-ACT and sup-
port up to 64 architecture-specific operations. For example, HBM-
PIM [40] can leverage PIM-ACT to encode 35 commands that are
actually used in practice. The optype field specifies both the op-
eration and its operand sources and destination, offering detailed
instruction semantics. Also, considering PIM requests according
to data direction–write (host-to-PIM) vs. read (DRAM-to-PIM)–
ComPASS combines this with an optype to express over 64 effective
operations in a single PIM-ACT format.
When the MC receives a PIM read or write request, it issues
PIM-ACT if the target row is not already activated. After tRCD
cycle, the MC can issue a column command for the PIM request.
If subsequent PIM requests share the same optype and row, they
are treated as row hits and issued at tCCD_L (column-to-column
delay within bank group) interval. Otherwise, if a request targets
a different row, the MC must first precharge all banks using the
standard PREA command.
4.2 System Support to Exploit PIM-ACT
To ensure the issuance of PIM commands through PIM-ACT, the
MC must receive PIM read/write requests in the specified sequence.
In this case, PIM requests must be generated at an extremely high
frequency to fully utilize the maximum PIM bandwidth, which
places a substantial load on host processors (i.e., CPU, GPU, or
NPU) [35]. For example, in HBM-PIM, where read or write requests
are utilized to perform PIM operations, up to 1,024 threads gener-
ate memory requests to achieve maximum PIM bandwidth. This
approach leads to excessive host processor core usage during PIM
operations, ultimately degrading overall system performance. To
alleviate this burden, we propose to add a PIM request generator
within the MC, which breaks down macro-level requests from the
host into micro-level PIM requests (Figure 4(a)).
As shown in Figure 4(b), the PIM request generator consists of a
request buffer to store macro-level requests, a data buffer that holds
the data necessary for processing these requests, and a decoding
logic. The core issues a macro request that defines the optype,
starting address of the operand, and operation length, to the PIM
request generator. Then, the PIM request generator decodes it and
generates multiple micro PIM read or write requests to the MC’s
request queue. The MC schedules these micro PIM requests with
regular memory requests and issues PIM-ACT and RD (or WR)
commands to process them. While request generation is a general
concept, ComPASS enables a single, unified generator to support
diverse PIM devices by standardizing the macro interface, as further
detailed in the following sections.
4.3 The Details of Macro and Micro Requests
Figure 4(c) shows the detailed structure of PIM macro and micro
requests and the corresponding DRAM commands. A macro request
comprises a 1-bit completion flag, a 1-bit RW indicator, a 6-bit
optype, a 40-bit address, and a 16-bit length field, totaling 64 bits.
This design allows the processor to issue macro requests that align
with its cache-line size. The completion bit indicates whether all
associated micro requests have been issued, while the RW indicator
specifies the request type between read and write. The optype field
defines the PIM operation, and the address field specifies the starting
physical address for the macro request. The length field indicates
the length of the operation, specifying how many read or write
micro requests are needed to complete it. For PIM write requests,
however, the length field is split to represent both the operation
length and the offset of the data buffer address, as data must be
supplied from the data buffer within the PIM request generator.
The 40-bit address field supports up to 1 TB of addressable mem-
ory space, sufficient for typical CPU or mobile system requirements.
The address and length fields are adjustable because they are system-
dependent. If the system’s memory capacity increases, the address
field can be extended, or the address can be modified to exclude
the cache-line offset, thereby expanding the addressable capacity.
Conversely, if 40 bits for the address are not required, the address
field can be reduced, allowing more bits to the length field.
A micro request consists of the same fields as a macro request,
except for the completion bit and length fields. Each micro request
represents a PIM read or write and specifies the type of PIM opera-
tion to be performed. The MC schedules PIM micro requests with

4.4 Managing PIM Request Generator
Processors can access the PIM request generator’s buffers via memory-
mapped IO (MMIO). This access is managed by the OS kernel and
PIM libraries as a privileged operation and protected as a critical
section to ensure exclusive access from multiple cores. To initiate
a task, the host processor writes macro requests and data to their
respective buffers and then triggers the PIM request generator via
MMIO. The completion status of macro commands can be mon-
itored either through polling or an interrupt-driven method. In
the polling approach, a designated core periodically checks the
completion bit, though this may introduce additional overhead to
the processor core. Alternatively, we leverage an interrupt-driven
method where the MC sends an interrupt to the processor upon task
completion. To prevent frequent interrupts, the PIM request genera-
tor triggers an interrupt only when the completion bits of all macro
requests are set. Upon receiving the interrupt, the processor reads
the completed PIM results to proceed with subsequent operations
or sends new macro requests to initiate other PIM operations.
Modern computer systems are typically equipped with multiple
MCs, each managing a distinct physical memory address range.
In such systems, a dedicated PIM request generator is placed on
each MC, generating micro requests for its local memory space.
The host processor sends macro requests to each MC’s generator
individually and treats the PIM operation as complete only after
receiving completion interrupts from all involved generators.
To support this coordination, the PIM vendor’s software stack is
expected to abstract multi-MC management by generating appro-
priate macro operations from user-level requests, synchronizing
execution, and collecting completion signals from all PIM request
generators, possibly with custom address mapping. Alternatively,
since ComPASS is a protocol-level solution compatible with vari-
ous PIM devices, the OS can provide a common runtime support
(e.g., PIM libraries) to route macro requests to multiple PIM request
generators and synchronize them, excluding vendor-specific tasks
such as address mapping and macro request generation.
4.5 Architecture-Aware Optimization of
PIM-ACT
ComPASS enables architecture-aware protocol optimizations (AAO)
by flexibly leveraging PIM-ACT and optype support. Depending
on the characteristics of the target PIM device, ComPASS allows
tuning of DRAM timing parameters and bank ACT granularity
to maximize execution efficiency. This tuning is enabled through
information provided by the Serial Presence Detect (SPD [ 20]),
which allows the MC to adapt behavior based on device-specific
characteristics. By enabling AAO, ComPASS supports architectural
optimizations without losing protocol compatibility or adding host-
side complexity. Note, however, this assumes a single PIM device
type per host processor, with customization applied accordingly.
First, some PIM operations do not involve DRAM row ACT. For
example, commands that transfer data from the processor to PIM
internal registers or buffers, or move data between PUs, do not ac-
cess DRAM cells and therefore do not require ACT. For such cases,
using the standard DRAM row timings–such as tRCD, tRAS (row
active time), and tRP (row precharge time)–is unnecessarily conser-
vative for PIM-ACT. Instead of introducing new command types,
ComPASS supports per-optype timing customization, allowing the
MC to apply tighter row timings based on optype. These per-optype
row parameters are provided through SPD and loaded by the MC at
boot time, enabling efficient execution without requiring changes
to the overall protocol.
Second, for PIM architectures that activate rows at finer granu-
larity (e.g., bank-level or bank-group-level ACT [27, 30, 31, 34, 60]),
maintaining a common open row across all banks is unnecessary.
In these cases, the SPD can specify whether each optype applies
to all banks or a subset. This allows the MC to manage bank states
independently, reducing unnecessary PREA and PIM-ACT over-
head. However, a portion of the optype bits must be reserved to
specify the target bank, reducing the available encoding space for
PIM operations. One approach to address this limitation is to extend
PIM-ACT with additional cycles, utilizing the multi-cycle command
described in Section 4.1. For example, adding one extra cycle to the
command (e.g., in an HBM3 system) provides 8 additional bits for
optype, which can encode both bank IDs and compute semantics.
Although this appears to increase tRCD, it can be resolved by speci-
fying the target bank in the optype portion of the initial cycles and
encoding the PIM operation in the final cycle.
Third, for compound operations where multiple computations
are executed sequentially using a single DRAM column command

4.6 Address Space Management for PIM
A macro request generates a specified number of micro requests
that begin at a specific physical address, striding by memory access
size units. Therefore, data for PIM operations must be stored in a
physically contiguous memory. To ensure this, we use HugeTLB [9]
feature to allocate PIM data on huge pages (2MB or 1GB), depending
on the required data size. Prior studies [45, 50, 63] also adopt huge
pages to maintain contiguous memory allocation for PIM. HugeTLB
dynamically allocates huge pages even when PIM operations run
alongside regular applications, preventing PIM data from being
swapped out. Additionally, when memory fragmentation prevents
direct huge page allocation, the memory compaction feature [13]
can be leveraged. While compaction introduces overhead, PIM tar-
get applications like LLM inference repeatedly access preallocated
memory over long inference sequences, amortizing the initial al-
location cost. However, for shorter PIM workloads, the overhead
may become more pronounced, and potential system-wide impacts,
such as performance interference with co-running applications,
remain important considerations for future quantitative analysis.
4.7 Applying Proposed PIM Protocol to Existing
PIM Architectures
To demonstrate the compatibility of ComPASS, this section illus-
trates how it can be applied to commercially available PIM archi-
tectures, unifying them under a single protocol without requiring
major design changes. Table 1 shows how ComPASS applies to
HBM-PIM [40] and GDDR6-AiM [38]. Optypes 0-31 are assigned
to computation operations, and 32-63 to data transfer operations,
simplifying decoding logic. HBM-PIM and GDDR6-AiM use 35 and
32 optypes, respectively. The same operation can be classified into
different optypes depending on its source and destination.
In HBM-PIM, MUL, ADD, and MAD use eight optypes each,
while MAC uses two. These commands involve reading data from
the DRAM banks, so they are treated as read requests. In contrast,
ReLU uses four optypes, operating on GRF data within the PU
and writing results back to DRAM, making it a write request. MOV
command uses five optypes based on the source and destination. For
transfers between banks and GRFs, the request type (read or write)
also determines the source and destination. When transferring
data from the host processor (i.e., data buffer) to the register file
(RF) within the PU, the address field specifies the type of RF (i.e.,
GRF, SRF, or CRF). Since these accesses do not involve DRAM row
ACT, they are handled using PIM-ACT commands with row timing
adjusted by AAO. Although ReLU and MOV are write requests,
they transfer data internally between banks and PUs, and the PU
ignores data from the host.
In GDDR6-AiM, although operations are more granular, fewer
source-destination pairs reduce required optypes. Since GDDR6-
AiM supports four-bank MAC (MAC4B) and all-bank MAC (MACAB),
MAC operations are encoded using five optypes with AAO: four
for MAC4B and one for MACAB. EWMUL also uses five optypes,
as it can operate on each bank group independently or across all
bank groups. AF (activation function) accesses only internal regis-
ters, making it suitable for row timing AAO. For RDCP and WRCP,
which move data between G-buf and a specific bank, sixteen op-
types with AAO are used to distinguish among the 16 banks. Other
operations use a single optype each, with the data transfer direction
indicated by the read/write request type. Like HBM-PIM, transfers
between the host and internal registers (MAC_REG, AF_REG, and
G-buf) benefit from row timing AAO. If a write request does not
require host data, the PU simply ignores the transferred data.
Figure 5 presents an example PIM request generator API and
pseudo-codes for executing GEMV on HBM-PIM and GDDR6-AiM
with the PIM request generator. The operand matrix is horizontally
partitioned across the DRAM banks. As shown in Figure 5(a), the
functions send_PIM_req() and send_PIM_data() send requests
and data to the memory-mapped request buffer and data buffer
within the PIM request generator, respectively, while the function
run_PIM_request_generator() initiates the PIM request gener-
ator to transmit micro-requests to the MC request queue. This
process is common for both HBM-PIM and GDDR6-AiM.
For HBM-PIM (Figure 5(b)), the GRF holds only a segment of
the input vector (sub-vector) due to the size constraints. Thus, the
GRF must be updated with another sub-vector upon completion
of each operation. The overall GEMV operation is performed in
the following sequence. 1) The processor writes the entire input
vector to the data buffer of the PIM request generator. 2) For each
sub-vector, the processor sends macro PIM write and read requests
indicating writing a sub-vector to GRF and processing the MAC
operation, respectively. 3) Then, it sends macro write requests to
store the results back in the DRAM banks. 4) Finally, it triggers the
PIM request generator to generate micro PIM requests.
Figure 5(c) illustrates the pseudo-code for GEMV operations in
GDDR6-AiM. The overall operation flow is identical to that of HBM-
PIM, but two key differences exist: the input vector is held in the
larger G-buf instead of the GRF, and each output is read back by
the host processor rather than being stored in the DRAM bank.
5 Memory Scheduling with PIM-ACT Protocol
The proposed protocol introduces new memory request types, PIM
read and PIM write, along with a new DRAM command, PIM-ACT.
This addition necessitates a memory scheduler that can balance
PIM and non-PIM requests. Since PIM workloads are offloaded
to acceleration, ensuring sufficient PIM throughput to meet their
QoS is the top priority. While invoking PIM operations implies the
user’s intent to allocate bandwidth for in-memory computation,
fully stalling non-PIM applications can cause system-level issues.
Therefore, the scheduler should allow non-PIM requests to pro-
ceed without excessive delays. To achieve this balance, ComPASS
proposes scheduling strategies that prioritize PIM execution when
needed while allowing normal memory requests to proceed without
excessive delays. This section identifies key challenges in handling
mixed PIM and non-PIM memory access, analyzes the limitations of
prior scheduling policies, and proposes a new memory scheduling
solution for PIM-attached systems.

5.1 Bank State Transitions for PIM Requests
PIM requests are accompanied by PIM-ACT, which changes the state
of all banks within a channel. Therefore, the MC should consider
the following scenarios: 1) After processing PIM requests, a PREA
must be issued before non-PIM requests. 2) To initiate a PIM request
following non-PIM requests, PREA and PIM-ACT must be issued.
3) Successive PIM requests on the same row are treated as row hits,
but those targeting different rows or with a different optype require
PREA and PIM-ACT again. Since PREA is required to synchronize
bank states between PIM and non-PIM requests, frequent switching
should be avoided. Additionally, because PIM requests require PREA
when the target row changes, it is beneficial to process non-PIM
requests before issuing PIM-ACT again.
5.2 Limitation of Existing Scheduling Solutions
Prior scheduling policies like FR-FCFS [51] can be adapted to man-
age PIM and non-PIM requests. Figure 6 illustrates how various
scheduling policies process given request sequences. FR-FCFS min-
imizes unnecessary PREA and PIM-ACT commands by prioritiz-
ing row-hit requests after issuing PIM-ACT. However, if memory-
intensive non-PIM workloads generate many row-hit requests, PIM
execution is delayed significantly (Figure 6(a)). Conversely, non-
PIM requests may also suffer in FR-FCFS. Since non-PIM requests
can be processed with bank interleaving, handling multiple requests
simultaneously is advantageous. However, in FR-FCFS, non-PIM re-
quests are not guaranteed to be processed consecutively, as a single
preceding PIM request, which takes priority, delays all subsequent
non-PIM requests that cause row conflicts until all PIM requests
for that row are completely processed (Figure 6(b)). Using batch
schedulers like PAR-BS [44] improves balance by scheduling within
request batches, but they can fragment row-hit PIM requests across
batches. This leads to excessive PREA commands and degrades
memory performance (Figure 6).
To schedule bandwidth-heavy PIM workloads, Thread Cluster
Memory (TCM [36]) scheduler can be used, as it clusters threads
into latency- and bandwidth-sensitive clusters. It rotates memory
access priority among bandwidth-sensitive threads, helping distrib-
ute bandwidth across threads, but limiting PIM bandwidth when
multiple memory-intensive CPU threads are present. Also, if the
request queue is insufficient or the priority rotation interval is too
short, consecutive PIM requests to the same row can be fragmented,
increasing PREA and PIM-ACT overhead. With latency-sensitive
threads, PIM requests are always deprioritized, and even a single in-
terleaved non-PIM request can trigger PREA during a PIM burst. To
address these issues, we gradually propose two memory scheduling
solutions, static and adaptive throughput balancer.

for PIM and N for non-PIM–and schedules requests within the type
using FR-FCFS. Priority switches to the other type when: (1) the
number of consecutive requests of one type reaches the threshold,
(2) there are no more requests of the prioritized type, or (3) for PIM,

ST-BLC must select appropriate values for P and N to achieve
the desired performance. The value of P directly impacts both PIM
throughput and non-PIM latency. Larger P improves PIM through-
put but can delay non-PIM requests. Since a PREA is required when-
ever the target row changes, there is no benefit in setting P larger
than the number of columns in a DRAM row. Also, power-of-two
aligned P values (e.g., 16, 32) are preferred when P is smaller than
the full row. For example, in LPDDR5, a row contains 64 columns,
allowing up to 64 PIM requests per row. If P is set to 48, the MC
will issue a PREA after 48 PIM requests, serve N non-PIM requests,
and then re-issue another PREA to process the remaining 16 PIM
requests–resulting in two PREA operations for a single row. N is
less constrained and can be tuned based on the desired trade-off
between PIM and non-PIM performance; a higher value of N pro-
vides more throughput to non-PIM requests. However, setting both
P and N too low leads to frequent switching and increased PREA
overhead, reducing overall memory efficiency. Given these consid-
erations, we present a sensitivity analysis of P and N in Section 7.
5.4 Adaptive Throughput Balancer
Selecting an optimalN for the ST-BLC requires considering multiple
factors based on the characteristics of running workloads. A small
N ensures high PIM performance; but if PIM bandwidth demand is
low, it unnecessarily delays conventional workloads. Conversely, a
large N can hinder PIM throughput under memory-intensive non-
PIM workloads. Thus, a static approach may either fail to provide
stable performance for PIM workloads or hurt system efficiency. To
address this, we propose adaptive throughput balancer (AT-BLC),
which adjusts N dynamically at runtime based on PIM execution
progress. It ensures PIM QoS and allocates the remaining bandwidth
to conventional workloads.
AT-BLC monitors the number of PIM micro-requests issued
(𝑊𝑐𝑢𝑟 ) and the elapsed cycles (𝑇𝑐𝑢𝑟 ) since the start of the PIM oper-
ation. At every refresh interval, it adjusts N by a predefined delta
(d)–increasing N when PIM progress exceeds the target and de-
creasing it when progress falls behind. To enable this adjustment,
the target completion time (T) and total number of micro-requests
(W ) must be initialized before the PIM operation begins (prior to
the pseudo-code in Figure 5). T and W values can be derived from
the size of the PIM operation, and these calculated values are passed
to the MC during initialization. The progress of PIM operation is
evaluated based on the following two inequalities.

requests and PIM requests to be managed within a single queue.

and non-PIM requests, as they prioritize either PIM or non-PIM
requests at the top level. Thus, we add an additional queue dedi-
cated solely to PIM requests for these policies. Since PIM requests
are issued sequentially by the PIM request generator, and no fur-
ther reordering is required between them, this queue only has two
entries, incurring negligible area cost.

AT-BLC effectively monitors the progress of PIM operations
and dynamically adjusts its threshold, allowing it to operate effi-

target performance. When the demand for PIM execution is high,
AT-BLC maintains sufficient PIM cycles even as CPU bandwidth
demand increases. Conversely, when fewer PIM operations are re-

In contrast, the optimal N and P values for ST-BLC vary depend-

target. On the other hand, when the PIM workload is lighter GPT-3
XL, fewer PIM operations are required, and even higher N values
can meet QoS. Reducing the absolute values of N and P–even if
their ratio remains constant–results in more frequent PIM-ACT
commands, which significantly degrade system performance.

8 Related Works
Efficient PIM command processing with macro instruction:
To mitigate the burden on the core caused by issuing repeated PIM
commands, prior works proposed utilizing macro instructions that
encapsulate multiple micro commands [27, 32, 48, 54]. For example,
TRiM [48] and Darwin [32] incorporate instruction decoders and
generators within memory nodes to offload PIM command issuance.
However, this design prevents the MC from tracking the bank state,
resulting in normal memory requests being unable to proceed con-
currently and remaining pending until PIM execution is completed.
Similarly, AESPA [27] introduces a long-data command, which en-
ables PIM operations at the DRAM row level with deterministic
execution latency. However, it lacks consideration for the limited
memory command space defined by JEDEC standards, making it
difficult to be compatible with various systems.
PIM command scheduling with normal memory accesses:
Prior works [7, 17, 47, 54] focused on workload or application-level
scheduling techniques for PIM that optimize batching and pipelin-
ing, while command-level scheduling between PIM and normal
memory accesses remains relatively underexplored. One attempt to
address this issue [41] proposed gather & issue scheduling policy
which triggers PIM execution once the number of accumulated PIM
requests exceeds a predefined threshold. However, this approach
can lead to inefficient mode switching if the threshold selection does
not account for DRAM architectural characteristics, such as the
number of DRAM columns, thereby negatively impacting system
efficiency. Moreover, even with an appropriately chosen threshold,
when the PIM workload intensity is high, regular memory requests
experience excessive queuing delays, potentially leading to QoS
degradation. A recent work [15] proposes a PIM-aware MC that
separates PIM and regular memory requests using virtual channels
and schedules them based on arbitration targeting fairness and
throughput. This approach is conceptually similar to our ST-BLC,
as both coordinate priorities between PIM and normal memory
accesses. However, our work goes further by introducing AT-BLC
that adjusts scheduling dynamically to meet QoS targets, and by
proposing a unified protocol interface (PIM-ACT) for compatibility
across various PIM architectures.
9 Conclusion
We have proposed ComPASS, a novel PIM protocol and scheduling
solution designed to address the challenges of compatibility and
efficiency in PIM-attached systems. ComPASS introduces the PIM-
ACT command, which enables multi-bank activation by leveraging
the unused memory command space in JEDEC standards, and pro-
vides corresponding system support to ensure seamless integration
of PIM operations. It also supports architecture-aware optimiza-
tions through per-device customization, improving performance
without sacrificing protocol compatibility. Through case studies
with HBM-PIM and GDDR6-AiM, we demonstrate that existing
PIM architectures can be adapted to ComPASS without requir-
ing fundamental design changes. To further enhance PIM system
efficiency, we introduce static and adaptive throughput balancer
scheduling solutions, which effectively manage scheduling between
PIM and conventional memory requests. These solutions ensure
consistent PIM performance while serving memory requests from
general workloads within a reasonable latency. Our evaluation us-
ing GEMV operations for GPT-3 inference workloads demonstrates
that LPDDR-PIM with ComPASS reliably meets QoS targets for
token generation, improving the GEMV performance by 10.75×
compared to a system without PIM, even when executed concur-
rently with memory-intensive SPEC CPU workloads. These results
highlight ComPASS’s potential to enhance the compatibility of
future PIM-integrated architectures.
